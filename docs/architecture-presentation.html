Digital Foresight
Agent Factory

Architecture & Agent Catalog for “The Company”

A scalable multi-agent system that turns signals into publishable insights —
built for high information velocity, with traceability and governance.

Version 1.0 · May 2026
Opening frame: we're proposing an agent factory, not a single agent. Three things to remember: (1) hierarchical control plane + scalable pods, (2) every output is traceable to evidence, (3) human approval gates before anything customer-facing ships.

Purpose & outcomes

What we're building

  • Scalable multi-agent architecture for digital foresight
  • Customer-facing outputs for “The Company”
  • Designed for high information velocity

What it must deliver

  • Traceability & governance by default
  • Signals → publishable insights & products
  • Reusable capabilities + thin domain agents

Scale path: a handful of agents today → ~100 agents across 12 domains.

The "why" is volume + velocity + trust. Today an analyst can read maybe 50 signals/week well. We need to scan thousands and surface the 5–10 that matter — without hallucinating or losing the provenance trail.

Operating model

Hierarchical control + swarms of reusable agents.

Tier 0 Control

Small, stable Control Plane. Orchestration, policy, evals, knowledge store.

Tier 1 Core

Core Production Line. Ingest → enrich → score → cluster → draft → publish.

Tier 2 Upgrade

Optional Intelligence Upgrades. Credibility, red team, trajectory, scenarios, impact.

Tier 3 Pods

Domain Pods scale to ~100 agents. Reusable capabilities + thin micro-agents.

↓ press ↓ for the scaling principle

Why hierarchical + swarms

  • Stability where it matters — Tier 0 is small and changes rarely. Trust comes from here.
  • Speed where it matters — Tier 1 is a pipeline; each stage owns one thing.
  • Depth on demand — Tier 2 upgrades fire only when a signal justifies them.
  • Reuse over duplication — Tier 3 pods compose Tier 0–2 agents instead of cloning them.

Result: scale from ~10 agents to ~100 without 10× the maintenance.

Architecture — five logical layers

1. Sense — ingest and normalize signals from trusted sources
2. Make sense — enrich, score, deduplicate and cluster signals
3. Interpret — draft insights with evidence, confidence and actions
4. Package — publish briefs, dashboards, 1-pagers (with approval gates)
5. Learn — continuous evaluation, drift detection, feedback loops

Event-driven backbone · shared Knowledge Store (raw + structured + vectors + optional graph)

Every transition emits an event. Every event is auditable. Every published item carries trace metadata back to source.

Standard agent contract

Every agent — across all tiers — implements the same contract. This is what makes composition safe.

Triggers

Events (signal.created, cluster.updated…) or scheduled runs.

Inputs

Object reference, policy pack, “The Company” context pack, tool permissions.

Outputs

Structured JSON + human notes. Claims mapped to evidence. Trace metadata (agent name + version).

Non-functional

Idempotent · audit logs · draft/approved separation · cost & latency budgets.

Composable Auditable Bounded Replayable

Idempotency is the killer feature. It means we can replay any event safely without duplicating objects or outputs. Without it, retry storms become production incidents.

Canonical events

The bus is the integration contract. New agents subscribe; they don't call each other.

↓ drill into each agent

A0

Orchestrator / Workflow Director

Runs the end-to-end pipeline, routes work to pods/agents, enforces SLAs and review gates.

What it does

  • Advances objects through workflow states
  • Routes by taxonomy, relevance & audience
  • Allocates compute budget; invokes specialists only when needed
  • Enforces human-in-the-loop approval gates
  • Retries, dead-letter queues, run observability

I/O

In: workflow defs, agent registry, policy pack, taxonomy, SLA rules

Out: agent-run.created agent-run.completed agent.error workflow.audit

Acceptance:
  • ≥99% workflows complete without manual intervention
  • Idempotent retries (no duplicate objects/products)
  • Every published item has full agent-version + evidence trace
A1

Policy & Compliance Gatekeeper

Governance, data classification, IP/copyright-safe publishing.

What it does

  • Validates sources against allow/deny lists + licensing
  • Applies classification: public / internal / restricted
  • Blocks copyrighted text beyond allowed limits; enforces citation-first
  • Flags sensitive info; suggests redactions
  • Hard gate: only approved insights ship

I/O

In: policy pack, source registry, classification rules, templates

Out: policy.pass policy.block redaction.suggested

Acceptance:
  • 0 policy violations in published products during pilot
  • 100% of published insights carry citations + provenance
  • All blocks include reason + remediation
A2

Quality & Evaluation (Evals) Agent

Measures quality, usefulness, drift and regression for every agent/version.

What it does

  • Maintains labeled test sets (relevance, clustering, usefulness)
  • Runs scheduled evals; gates promotion of new versions
  • Detects input drift (source mix, topic shifts) and output drift
  • Weekly dashboard: precision/recall, novelty, latency, cost/insight

I/O

In: eval datasets, feedback signals, version registry, thresholds

Out: eval.report.created eval.regression.alert

Acceptance:
  • Weekly eval report generated automatically
  • Agent updates blocked if regression > thresholds
  • Metrics visible to owners and stakeholders
A3

Knowledge Store Librarian

Storage, indexing, retrieval bundles, provenance across the knowledge base.

What it does

  • Stores immutable raw artifacts with hashes
  • Generates embeddings; maintains vector index
  • Maintains entity index + optional knowledge graph
  • Provides retrieval packs (top-k, similar, domain context)

I/O

In: blob store, DB, vector store, schema versions, retention rules

Out: retrieval.pack.created index.updated

Acceptance:
  • 100% signals reference retrievable raw artifacts
  • Top-k retrieval latency within SLA
  • Provenance consistent and queryable

B1

Ingestion Coordinator

Collects signals from external + allowed internal sources with robust coverage reporting.

What it does

  • Source registry: RSS, APIs, web, newsletters, standards bodies, patents
  • Fetches content, extracts main text, stores raw artifact + Signal header
  • Initial source reputation + domain hints + retrieval metadata
  • Emits daily source health report

I/O

In: source registry, cadence schedule, parsing rules, secrets

Out: signal.created sources.health.report

Acceptance:
  • ≥95% successful fetch cycles
  • Duplicate raw fetch <5% (hash-based)
  • Daily coverage report (alive/dead sources)
B2

Normalization & Enrichment

Cleans and enriches signals with standardized summaries, entities, taxonomy and type.

What it does

  • Boilerplate removal & text cleaning
  • Language detection + optional translation (preserve original)
  • Extract entities (ORG/TECH/GEO/PERSON) + key phrases
  • Generate short abstract + key takeaways
  • Taxonomy + signal type (regulation, research, incident, funding, release…)

I/O

In: signal.created, taxonomy, domain dictionaries

Out: signal.enriched

Acceptance:
  • ≥90% signals labeled with taxonomy + type
  • Summaries accurate to source & within length limits
  • ≥80% non-trivial signals have ≥1 entity extracted
B3

Relevance & Routing — “The Company” Lens

Scores relevance/novelty/urgency and routes signals to domain pods and audiences.

What it does

  • Scores: relevance, novelty, urgency, impact, credibility baseline
  • Routing tags: domains, themes, personas, time horizon
  • 2–3 bullet rationale: “why this matters for The Company”

I/O

In: signal.enriched, lens profiles, historical archive

Out: signal.scored

Acceptance:
  • Precision ≥0.75, recall ≥0.70 for 'high relevance' on labeled set
  • ≥95% high-relevance signals have coherent rationale
  • Latency signal.created → scored within SLA
B4

Deduplication & Clustering

Reduces noise and builds storylines across time windows.

What it does

  • Near-duplicate detection (hash + similarity)
  • Cluster signals into storylines with labels and descriptors
  • Detect bursts + persistent growth; flag emerging themes

I/O

In: signal.scored, embeddings, window config

Out: cluster.updated

Acceptance:
  • Reviewers report ≥30% reduction in repeated reading
  • Cluster labels coherent ≥80% for top clusters
  • Burst detection: ≥8/10 obvious spikes in backtest
B5

Insight Drafting — So-What for “The Company”

Turns clusters into decision-relevant insight drafts with evidence, confidence and actions.

What it does

  • Standard template: what happened · evidence · implications · time horizon · uncertainties
  • Recommended actions: watch / experiment / engage + owners
  • Two versions: Exec one-pager + Analyst detail
  • Explicit confidence and uncertainty language

I/O

In: cluster.updated, retrieval pack, context pack

Out: insight.created

Acceptance:
  • ≥90% insights include ≥3 citations
  • Usefulness ≥3.5/5 avg after review
  • Every insight: time horizon + explicit uncertainties
B6

Publishing & Distribution

Compiles approved insights into briefs, dashboards and notifications.

What it does

  • Weekly brief + monthly theme deep dives from approved insights
  • Update dashboards: trend radar, cluster timelines, watchlists
  • Publish to SharePoint / Teams / email with audience ACLs
  • Product history + changelog

I/O

In: insight.approved, templates, calendar, audience ACLs

Out: product.published

Acceptance:
  • Weekly brief produced within SLA
  • Only approved insights publish (hard gate)
  • Artifacts include citations + trace metadata

C1

Evidence & Credibility

Triangulates claims, scores credibility, reduces hype, adds evidence notes.

What it does

  • Credibility score from source reputation + corroboration
  • Flags speculative vs confirmed; maps claims to evidence
  • Suggests what additional evidence would raise confidence

Acceptance

  • ≥80% 'high confidence' insights have ≥2 independent sources
  • Reviewers report fewer 'hype' items after introduction
  • All credibility adjustments are explainable
C2

Contrarian / Red Team

Challenges assumptions, provides counterarguments and falsification tests.

What it does

  • Strongest counterargument + alternative interpretations
  • Failure modes + what evidence would falsify the insight
  • Balanced language + caveats for publication

Acceptance

  • ≥70% of high-impact insights improved by red-team pass
  • Red team notes professional & evidence-based (no opinion-only)
C3

Trend Trajectory

Tracks clusters over time; detects acceleration, deceleration and inflection points.

What it does

  • Per-cluster time series: volume, source diversity, geo spread
  • Detect inflection points + leading indicators
  • Stage label: emerging / growing / mature / declining

Acceptance

  • Backtest identifies ≥8/10 obvious accelerations
  • Trajectory notes align with analyst judgement ≥70% in pilot
C4

Scenario Hooks

Maps signals to scenario assumptions and triggers alerts when assumptions shift.

What it does

  • Maintain assumption register + thresholds
  • Map clusters to assumptions strengthened/weakened
  • Trigger scenario hook alerts with rationale + evidence

Acceptance

  • Scenario hook alerts relevant ≥70% in pilot
  • Every alert includes rationale + evidence links
C5

Impact & Dependency Mapper

Transforms insights into value-chain impact maps and dependency/risk registers.

What it does

  • Identify impacted value chains + key dependencies (vendors, standards, regulation, skills)
  • Propose mitigation / enablement / experimentation options
  • Populate structured risk/opportunity register entries

Acceptance

  • Stakeholders rate impact maps actionable ≥3.5/5
  • Every high-impact insight has ≥1 proposed action + owner

How the tiers deploy on Azure

Tier 0 — Control Plane

Shared Container Apps environment · hardened · private VNet · restricted RBAC. Changes rarely. Active/standby across regions for DR.

Tier 1 — Core Production

Second Container Apps environment. Each B1–B6 is a revision-versioned app. KEDA scales on Service Bus queue depth.

Tier 2 — Upgrades

Invoked only when A0 routes a high-value insight. Use Container Apps Jobs (on-demand) to keep cost down.

Tier 3 — Pods

One Foundry Project per domain pod. Pod Lead is a Container App that calls shared Tier 0–2 + the pod's own micro-agents.

Subscriptions: prodnonproddata (Knowledge Store) shared (APIM, Front Door) — all inside an Azure Landing Zone.

The three enterprise decisions that matter most

1. Landing zone first

Drop this into an Azure Landing Zone — hub-spoke, policy-as-code, corp connectivity. Don't roll your own networking. Subscriptions: prod / nonprod / data / shared.

2. PTU vs PAYG for OpenAI

At ~100 agents the hot path (B3, B5, pod synth) needs Provisioned Throughput Units — predictable latency, capped cost. PAYG for tail + Tier 2 specialists.

3. Purview as governance backbone

Wire Blob, Cosmos and AI Search into Microsoft Purview. Classification (A1) and lineage (published → cluster → signal → raw) become centrally queryable.

These three are load-bearing. Getting them wrong means re-platforming later. Get them right and the rest is incremental.

Tradeoff — Foundry Agents vs. custom Container Apps

AI Foundry Agent Service

✓ Faster to ship
✓ Threads, tool use, evals for free
✓ Versioning + tracing built in

✗ Opinionated, newer surface
✗ Less control over idempotency keys, retry semantics

Custom Container App

✓ Full control over state, retries, gates
✓ Use any framework (Semantic Kernel, AutoGen, LangGraph)
✓ Mature ops story

✗ More code to own
✗ You build threading, tracing, eval hooks yourself

Pragmatic mix: Tier 0 + B1/B4/B6 as custom Container Apps · B2/B3/B5 + all Tier 2 + pod micro-agents as Foundry Agents
